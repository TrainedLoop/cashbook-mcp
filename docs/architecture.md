# Architecture

One Python 3.13 process built on FastMCP serves the MCP endpoint, the `/admin` page and `/health`. A background task keeps a local encrypted DuckDB file in sync with Pluggy; tools only read that file.

```
claude.ai --HTTPS--> tunnel (Funnel) --> container :8743
                                          |- /mcp          MCP tools (Google login)
                                          |- /admin        SPA + JSON API (Google login, session cookie)
                                          |- /health
                                          `- sync task --> Pluggy API (GET, POST /auth, POST /connect_token)
data/cashbook.duckdb (encrypted)   secrets/ (read-only mount)
```

## Storage and sync

- One DuckDB file, `data/cashbook.duckdb`, encrypted with DuckDB's native encryption. The key is `secrets/db.key`, generated by `cashbook-admin init`. The server refuses to start with a missing or wrong key.
- At startup the server runs migrations (copying the file to `cashbook.duckdb.bak-<version>` first), serves existing data and starts a background load. A full load runs daily at `REFRESH_AT` (timezone `TZ`); an hourly check calls `GET /items/{id}` and loads a connection when `lastUpdatedAt` advanced.
- Each connection merges in one transaction: rows Pluggy returned are upserted, rows inside the fetched date range that Pluggy no longer returns get `removed_at`, and older rows are left alone. That is how history outlives Pluggy's window. On error the transaction rolls back and the error is recorded on the connection.
- Each successful load also writes one balance snapshot per live account and investment for the day, which feeds `net_worth`.
- Disconnecting an alias deletes it and all its rows (transactions, snapshots, account settings, overrides; journal rows stay), then reclassifies the remaining rows in the same write so none points at a deleted one. There is no history carry-over between items.
- DuckDB runs with `memory_limit` 256 MB and `threads` 2; the container is limited to 512 MB.

## Scopes and `v_flows`

Each connection has a role, `personal` or `business` (suggested from a 14-digit owner tax id when it is added, confirmed by the owner). The view `v_flows` is the one definition of income, spending, refunds and the money moving between personal and business: every row gets a `flow` (`income`, `spending`, `refund`, `from_business`, `to_business`, `from_personal`, `to_personal`, `internal`, `investment`, `card_payment`, `foreign`) plus `spend_amount` and `income_amount`. `analysis/metrics.py` turns a scope into a filter over it:

- `personal` (default): personal connections. Income includes what came from the business, reported apart as `from_business`; payments to the business are reported apart as `to_business`.
- `business`: business connections. Owner draws (`to_personal`) and contributions (`from_personal`) are reported apart, not as spending.
- `consolidated`: everything; transfers between roles are excluded.

Refunds reduce spending in the group they belong to, so the categories of a period add up to its spending. Agent SQL should use `v_flows` for money totals; `describe_schema` gives the personal income query that matches `cash_flow`. With a scope, `search_transactions` and raw `kinds` summaries leave out internal movements by `flow` (`internal`, `card_payment`), so transfers between personal and business show up; without one they leave out the internal kinds, as in v0.1.

## Classification pipeline

Kinds are derived inside one write transaction after every load, role or purpose change and reclassification, in this order:

1. per-transaction rules: bill matches, own-account and owner tax id matches, Pluggy category kinds, then the sign. On an account marked `investment`, an unidentified movement becomes `investment` (`investment_account`) instead of spending or income;
2. manual overrides (`manual:<change_id>`);
3. pairing of an outflow and an inflow of the same amount within three days across own accounts (`paired_with:<id>`). Pairing only rewrites guessed kinds; manual sides are never rewritten. A manual `internal_transfer`, `card_bill_payment` or `investment` side counts as evidence; any other manual kind rules the pair out.

## The local write path

Toward Pluggy the server is read-only. Locally there is exactly one write path available to the agent: `reclassify_transactions` sets the `kind` and/or the category of specific transactions. Each call is one journaled batch (`classification_changes`, with a short cleaned note) plus overrides per transaction: kinds in `classification_overrides`, categories in `category_overrides`, so a batch that changes one never erases the other. A category override only relabels the transaction in `v_flows` (`pluggy_category` becomes the effective category, `pluggy_category_original` keeps the provider's, `category_overridden` flags it); it never changes the kind, and classification keeps reading the provider's category. Valid categories are the ones present in the store plus `EXTRA_CATEGORIES` (Rent, Housing, Utilities, Education, Childcare); anything else is rejected with `bad_category`. `undo_reclassification` removes the kind and category overrides that still point to the batch, and a later batch replaces an earlier one for the same transaction and field. Batches are limited to 200 ids and the day to `MAX_RECLASSIFY_PER_DAY` changed transactions (calendar day in `TZ`). Notes are agent-written text, cleaned and returned marked as notes. Everything else in the store, and every request to Pluggy, stays out of the agent's reach. `review_classification` lists what the server is unsure about, with hints (kinds and categories) from earlier manual changes, and flags transactions whose counterpart was recategorized before (`same_payee_recategorized`); the server never applies a hint or a rule.

## The SQL tool

`query_sql` accepts exactly one `SELECT` (or `WITH`) statement; the type comes from DuckDB's parser, not a regex. It runs on a separate reader connection opened after the encrypted file is attached and then locked with `enable_external_access=false` and `lock_configuration=true`: no files, network, extensions, `ATTACH`, `COPY`, `SET`, `PRAGMA`, `INSTALL`, `LOAD` or writes. Limits: 10 s timeout and 1,000 rows (with a `truncated` flag). Cells that contain an untrusted marker are listed in `suspicious_cells`.

## Untrusted text

Counterpart names, descriptions and payment messages are written by third parties. They are cleaned (the marker characters U+27E6 and U+27E7 are stripped), capped at 500 characters, and wrapped in `⟦untrusted:suspicious⟧ ... ⟦/untrusted⟧` when a heuristic flags them. Tool descriptions state that text columns are data, never instructions.

## Authentication

- The MCP connector uses Google OAuth through FastMCP. Only emails in `ALLOWED_EMAILS` are issued a token; redirect URIs are limited to `ALLOWED_REDIRECT_URIS` (the Claude callbacks by default).
- `/admin` uses a server-side Google OIDC login and a signed `HttpOnly`, `Secure`, `SameSite=Strict` cookie on `Path=/admin`. Mutating calls need `X-CSRF-Token` and a matching `Origin`; disconnecting needs recent re-authentication.
- Items added in `/admin` are validated server-side: `GET /items/{id}` must succeed with the server's API key, the connector must be MeuPluggy, and the item and alias must be unused.

## Read-only toward Pluggy

The Pluggy client makes GET requests plus `POST /auth` (API key) and `POST /connect_token` (the Connect widget). Nothing else is sent. `GET /v2/transactions` is used; the deprecated `GET /transactions` and `GET /identity` are never called.

Connecting banks runs in the owner's browser, with the short-lived connect token. MeuPluggy shares each bank linked there as its own item, all under one login. The widget creates them the first time. Pluggy cannot list items on personal accounts, and once one MeuPluggy item exists, the `avoidDuplicates` token makes Pluggy refuse a new one (`ITEM_USER_ALREADY_EXISTS`) and name the existing ids. After the widget succeeds or fails, the SPA repeats that request (`POST /items` with the connect token, the same call the widget makes) only to read those ids, then sends them to `POST /admin/api/connections/discover`, which validates each one like any other item. The owner picks an alias per bank.

## Threat model

Defended: unauthenticated access, prompt injection through transaction text, agent-written SQL, CSRF and replayed callbacks on `/admin`, foreign Pluggy items, theft of the disk or of a copy of the database file.

Not defended: a shell on the host. That attacker holds the Pluggy client secret and can read the current window live. Persistence adds two exposures: history older than Pluggy's window, and data that survives revoking the Pluggy credentials.
