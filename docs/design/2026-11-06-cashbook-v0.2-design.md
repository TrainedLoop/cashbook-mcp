# cashbook-mcp v0.2: scopes, net worth, reclassification, forecast and alerts

Status: proposed
Date: 2026-11-06
Builds on: [2026-11-06-cashbook-mcp-design.md](2026-11-06-cashbook-mcp-design.md) (v0.1) and the transfer pairing pass (PR #15).

## Context

v0.1 runs on a real store. On that data, three problems came up:

- **Company and personal money were mixed.** Many owners run a company account (CNPJ) next to their personal ones. v0.1 treats every connected account as "the owner's", so client payments into the company account counted as personal income, company costs (taxes, services) counted as personal spending, and the money the owner actually takes out of the company vanished as an internal transfer.
- **Totals disagreed.** "Spending" was defined in three places (`v_spending`, `summarize._aggregate`, `cash_flow`). `cash_flow` nets refunds out of spending and the category breakdowns do not, so a month's spending and the sum of its categories differ by the month's refunds.
- **Some classifications are guesses.** Pairing fixes most transfers between own accounts, but some movements still cannot be told apart from the data alone: transfers with no counterpart document, broker cash accounts whose stock purchases arrive categorized as "Shopping", payments from relatives. The agent should be able to ask the owner and record the answer.

v0.2 also adds features that need the store to exist for a while (balance history), or that the agent gets wrong when it has to assemble them in SQL (cash forecast, changes in recurring charges).

v0.2 is a **breaking release**: the database is recreated (see Rollout).

### Goals

- Three **scopes** over the same data: `personal` (default), `business` and `consolidated`. Each connection has a role (`personal` or `business`).
- **One definition** of income, spending, refunds and the flows between personal and business. It lives in a SQL view, so tools and agent SQL use the same numbers. The categories of a period add up to that period's spending.
- **Balance history and net worth**: daily snapshots from now on, plus an estimated history for bank accounts.
- **Agent reclassification**: the agent can change the `kind` of specific transactions after asking the owner. Changes are journaled, reversible and capped. A **review queue** lists what the server is unsure about, with hints from earlier manual changes.
- **Broker cash accounts**: an account can be marked as an investment account, so unidentified movements there count as investment, not spending or income.
- **Cash forecast** for the next 30 to 90 days from known commitments.
- **Recurring changes**: price increases, new, stopped and duplicated recurring charges.

### Non-goals

- Income tax (IRPF) reports, and splitting company withdrawals into pró-labore and profit distribution.
- Push notifications. Alerts surface when a routine or the owner asks.
- Server-side rules that classify future transactions automatically. The agent decides each change; the server only shows the history of earlier changes as hints (see Reclassification).
- Role per account. Role is per connection; Open Finance consents are per CPF or per CNPJ, so one connection does not mix personal and company accounts in practice.
- Budgets, tags and user categories (unchanged from v0.1).
- Any write to Pluggy (unchanged, permanent).

### What changes in the v0.1 principles

v0.1 said the server is read-only. v0.2 keeps it **read-only toward Pluggy and the banks**, and adds **one local write path**: the agent can set a transaction's `kind`. Nothing else in the store is writable by the agent. The v0.1 non-goal "server-side notes" is relaxed for one field: a short note on each reclassification batch.

### Threat model additions

- The new write path can be driven by prompt injection in transaction text. The blast radius is local labels only: every change is journaled, every batch can be undone, batches and daily totals are capped, and every call is in the audit log. The tool description tells the agent to ask the owner before changing kinds it is unsure about. Responsibility for each change stays with the agent and the owner. The server does not try to judge intent.
- Reclassification notes are agent-written text. They are cleaned like third-party text, capped, and returned marked as notes, never as instructions.

The pipeline order inside `_reclassify` becomes:

1. per-transaction rules (v0.1, plus the investment-account default below);
2. manual overrides;
3. pairing across own accounts (PR #15). Manual sides are never rewritten by pairing, but count as evidence for it.

## Data model

### Connections and accounts

- `connections.role VARCHAR NOT NULL DEFAULT 'personal' CHECK (role IN ('personal', 'business'))`.
  When a connection is added, the admin suggests `business` if any of its bank accounts has a 14-digit owner tax id (CNPJ). The owner confirms or changes it.
- `account_settings(account_id PRIMARY KEY, purpose VARCHAR NOT NULL CHECK (purpose IN ('regular', 'investment')))`. A row exists only when the owner set a purpose; no row means `regular`. A separate table keeps settings out of the rows that sync upserts. Disconnecting deletes the connection's settings with its data.

### Card installments

`transactions` gains `installment_number INTEGER`, `installment_total INTEGER` and `purchase_date DATE`, read from Pluggy's `creditCardMetadata` (`installmentNumber`, `totalInstallments`, `purchaseDate`). Null when absent.

### Snapshots

```
balance_snapshots(day DATE, account_id VARCHAR, alias VARCHAR, balance DECIMAL(18,2), currency VARCHAR,
                  PRIMARY KEY (day, account_id))
investment_snapshots(day DATE, investment_id VARCHAR, alias VARCHAR, balance DECIMAL(18,2), currency VARCHAR,
                     PRIMARY KEY (day, investment_id))
```

After each successful load of a connection, sync upserts one row per live account and investment of that connection for today (in the configured `TZ`); a later sync on the same day overwrites. Loans are not snapshotted: their outstanding balance is read from `loans` for the current day only (see Net worth). Disconnecting deletes the connection's snapshots.

### Reclassification

```
classification_changes(change_id VARCHAR PRIMARY KEY, created_at TIMESTAMP, kind VARCHAR, note VARCHAR,
                       count INTEGER, undone_at TIMESTAMP NULL)
classification_overrides(transaction_id VARCHAR PRIMARY KEY, kind VARCHAR, change_id VARCHAR)
```

`classification_overrides` holds the current manual decision per transaction. A newer batch replaces an older override for the same transaction (the older batch's `count` is historical; undoing it only removes overrides that still point to it). `change_id` is a random URL-safe token. Disconnecting deletes the overrides of the connection's transactions; the journal rows stay.

### The `v_flows` view

`v_flows` is `v_transactions` plus:

| column | meaning |
|---|---|
| `role` | role of the row's connection |
| `peer_role` | for `internal_transfer` and `card_bill_payment` rows: role of the other side, else null |
| `peer_alias` | alias of the other side, when known |
| `flow` | one of `income`, `spending`, `refund`, `from_business`, `to_business`, `from_personal`, `to_personal`, `internal`, `investment`, `card_payment`, `foreign` |
| `spend_amount` | the row's contribution to spending: `-amount` for spending outflows, `-amount` (negative) for refunds, else 0 |
| `income_amount` | `amount` for income, else 0 |

`peer_role` comes from `kind_reason`:

- `paired_with:<id>`: the other transaction's connection;
- `counterpart_is_own_account:<alias>`: that connection;
- `counterpart_is_owner_tax_id`: the connection whose bank account has that tax id (a CNPJ points to the business connection, the owner's CPF to a personal one);
- `manual:<change_id>` and anything else: null.

`flow` is derived from `kind`, `amount`, `role` and `peer_role`:

- `kind = 'income'` → `income`; `purchase`, `fee`, `loan`, `other` outflows → `spending`; `refund` → `refund`; `investment` → `investment`; `card_bill_payment` → `card_payment`;
- `internal_transfer` or `card_bill_payment` between different roles → `from_business`/`to_business` on personal rows, `to_personal`/`from_personal` on business rows (for example, a personal account paying the company card is `to_business`); `internal_transfer` between equal roles or with unknown peer → `internal`;
- rows whose currency is not `BRL` → `foreign` (counted apart, as in v0.1).

`v_spending` is dropped. `schema_doc` documents `v_flows` as the place to compute money totals in SQL.

## Scopes and metrics

`metrics.py` turns a scope into a row filter over `v_flows` and exposes the totals every tool uses:

| | `personal` (default) | `business` | `consolidated` |
|---|---|---|---|
| rows | `role = 'personal'` | `role = 'business'` | all |
| income | `income` + `from_business` (reported apart as `from_business`) | `income` | `income` |
| spending | `spending` net of `refund` | same | same |
| reported apart, not spending | `to_business` | `to_personal` (owner draws), `from_personal` (owner contributions) | none |
| excluded | `internal`, `investment`, `card_payment` | same | same, plus all cross-role transfers |

Refunds reduce spending in the category (or merchant, account, period) they belong to, so grouped totals add up to the scope's spending.

Every response of a scoped tool states the scope it used.

### Tool changes

- `cash_flow(date_from, date_to, granularity, by_account, scope="personal")`: per period `income`, `refunds`, `spending`, `net`, plus the scope's apart lines (`from_business`, `to_business`, `owner_draws`, `owner_contributions`).
- `summarize_transactions(..., scope="personal")`: groups use `spend_amount` / `income_amount`; `group_by` accepts one dimension or a list of two (for example `["category", "month"]`), from the same whitelist.
- `list_categories(date_from, date_to, scope="personal")`.
- `finance_overview`: personal month to date as today, plus, when a business connection exists, a `business` block (income, spending, owner draws this month), a `net_worth` line (current, change this month) and a `forecast` line (lowest balance in the next 30 days, personal scope).
- `list_connections`: adds `role` and, per account, `purpose`.
- `search_transactions`, `get_transactions`: rows gain `role` and `flow`; filters gain `scope` (default: no scope filter, as today).

## Investment accounts

For an account with purpose `investment`, the per-transaction rules change only the sign fallback: an unidentified outflow becomes `investment` (reason `investment_account`), not `purchase`, and an unidentified inflow becomes `investment`, not `income`. Bill matches, own-account and owner matches, and category kinds (for example yields as income and income taxes as fees) win as before. Pairing still turns transfers to and from other own accounts into internal transfers.

## Net worth

`net_worth(scope="personal", date_from=None, date_to=None, granularity="month")` returns a series of points, each with `assets`, `liabilities`, `net` and a breakdown by `bank`, `investment`, `card`, `loan`.

- **Assets**: bank account balances plus investment balances. **Liabilities**: credit card balances (Pluggy reports the used amount; v0.1 Task 17 confirms the sign convention) and loan outstanding balances.
- A point uses the last snapshot on or before its date.
- **Estimated bank history**: before an account's first snapshot, its balance on day D is the first snapshot's balance minus the sum of the account's transactions after D and up to that snapshot's day. These points carry `estimated: true`. Investments, cards and loans have no estimate; their series starts at the first snapshot, and the response lists `history_starts` per component.
- Loans contribute only from the current day (no loan history exists).

## Reclassification

### Tools

- `reclassify_transactions(ids: list[str], kind: Kind, note: str | None = None)`:
  - 1 to 200 ids per call; each must exist and be live; unknown ids reject the whole call;
  - `kind` must be one of the existing kinds;
  - `note` is cleaned and capped at 200 characters;
  - daily cap `MAX_RECLASSIFY_PER_DAY` (default 1000) on changed transactions, per calendar day in the configured `TZ`; over the cap, the call is rejected with the remaining allowance;
  - writes the journal row and overrides, runs `_reclassify`, and returns `change_id`, the changed count and, per id, the old and new `kind`;
  - annotations: `readOnlyHint: false`, `destructiveHint: false`, `idempotentHint: true`, `openWorldHint: false`. The description says to ask the owner first when unsure.
- `undo_reclassification(change_id)`: removes the overrides that still point to the batch, sets `undone_at`, runs `_reclassify`, and returns how many transactions went back to automatic classification.
- `list_reclassifications(limit=20)`: recent batches with id, time, kind, note, count and `undone_at`.

### Review queue

`review_classification(scope="personal", date_from=None, date_to=None, limit=20)` returns groups of live transactions without a manual override, grouped by counterpart (tax id, else account number, else the normalized counterpart name), each group with a reason:

- `unpaired_transfer`: transfer category (`Transfer…`, `Same person transfer…`), not paired, counterpart not recognized as the owner;
- `large_unidentified_inflow`: `income` by sign with amount at least `REVIEW_MIN_AMOUNT` (default 500.00);
- `uncategorized_card_credit`: `refund` with no Pluggy category.

Each group carries ids, dates, amounts, account alias, category, counterpart name (marked untrusted) and a **hint** when the same counterpart (same tax id or account number) has live manual overrides: the kinds used and their counts. The server never applies a hint.

### Prompt

`review_classifications`: fetch the queue, ask the owner group by group, call `reclassify_transactions` only for what the owner confirmed, and report the `change_id`s.

## Cash forecast

`cash_forecast(scope="personal", days=30, by_account=False)`, `days` from 1 to 90.

- **Start**: current balances of the scope's bank accounts.
- **Events** (date, amount, source, confidence, account):
  - **open card bills** due in the window and not yet paid (a bill is paid when a `card_bill_payment` row matched it);
  - **future installments**: for each card purchase series (same account, `purchase_date`, `installment_total`, amount), the installments after the highest number seen, one per later bill, on the card's usual due day (the most frequent due day of its bills); installments already in an open bill are not repeated;
  - **recurring charges and income** from `find_recurring` with `high` or `medium` confidence and a next date in the window. Bank-account recurrences are direct events. Card recurrences are added to the estimated future bill of that card, not as direct events.
- **Not in the curve**: company withdrawals and other irregular inflows. The response carries `typical_monthly_inflow` (the scope's average monthly income over the last 3 full months) with a note that it is not included.
- **Output**: `start_balance`, `events`, a running balance per day (per week when `days > 31`), `lowest` (date, value) and `negative_on` (first date below zero, or null). With `by_account`, the same per account.
- The tool description states the limits: no new card spending beyond recurring charges, no company withdrawals, confidence per event.

## Recurring changes

`recurring_changes(scope="personal", months=6)` reuses the recurring detection and returns only changes, each with the transaction ids as evidence:

- `price_increase`: the last amount is more than 5% and more than 1.00 above the typical amount;
- `new`: first seen in the last 60 days with at least 2 regular occurrences;
- `stopped`: the expected date passed by more than half a cadence with no charge;
- `duplicate`: same counterpart and amount twice within 3 days in one cycle.

Prompt `weekly_review`: `finance_overview`, `cash_forecast(30)`, `recurring_changes`, `review_classification`; summarize and list the questions for the owner.

## Admin page

- **Add connection**: the alias step shows a role selector, pre-set from the CNPJ suggestion.
- **Connections list**: each connection shows its role with a selector; each bank account shows its purpose (`regular` / `investment`) with a selector.
- API: `PATCH /admin/api/connections/{alias}` with `{"role": ...}` and `PATCH /admin/api/accounts/{account_id}` with `{"purpose": ...}`. Both are mutations (session, same origin, CSRF), not fresh-sign-in gated, and validate values against the allowed sets. Unknown alias or account: 404.
- Changing a role needs no reclassification (`v_flows` reads it live). Changing a purpose runs `_reclassify`.

## Error handling

- Scoped tools reject unknown scopes with a `ValueError` (tool error), like other bad arguments.
- `reclassify_transactions` and `undo_reclassification` run in one write transaction; any failure leaves the journal and overrides as they were.
- Unknown `change_id`, an already undone batch, unknown ids, dead ids, a bad kind or the daily cap: the call returns an error with a short reason, nothing written.
- Snapshot writes are part of the load's write transaction: a failed load writes no snapshot.

## Testing

- Unit tests per module: `v_flows` derivation (every `flow` value, peer role per reason), scope filters, refunds netted per group, two-dimension grouping, snapshots and estimated history, investment-account defaults, overrides vs pairing order, journal, undo, caps, review groups and hints, forecast events (bills, installments, recurrences, paid bills skipped), recurring changes.
- Server tool tests for every new and changed tool, including annotations and error results.
- Admin API tests for the two PATCH routes (session, CSRF, origin, validation, 404) and web tests for the selectors.
- **End-to-end scenario** with synthetic data: a business connection receiving client payments and paying taxes; business → broker → bank transfers, one side without a counterpart document; a card paid by PIX; a refund; a broker cash account with an unidentified stock purchase. It asserts each scope's income, spending and apart lines, that categories add up to spending, and that marking the broker account as `investment` moves the purchase out of spending.
- Before release: the before/after comparison on a copy of a real store, inside its container, as done for PR #15.

## Rollout

Release 0.2.0, marked breaking. Steps (documented in the tutorial and release notes):

1. stop the stack and upgrade to 0.2.0;
2. start 0.2.0. Migration 0002 wipes the store automatically: all v0.1 data is discarded and the schema is recreated. The migrator leaves an encrypted backup, `cashbook.duckdb.bak-1`, next to the database; it is the only copy of the old store;
3. reconnect the banks from `/admin`, confirm each connection's role, and mark broker cash accounts as `investment`;
4. after the first load, check `finance_overview` and `review_classification`.
