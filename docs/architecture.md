# Architecture

One Python 3.13 process built on FastMCP serves the MCP endpoint, the `/admin` page and `/health`. A background task keeps a local encrypted DuckDB file in sync with Pluggy; tools only read that file.

```
claude.ai --HTTPS--> tunnel (Funnel) --> container :8743
                                          |- /mcp          MCP tools (Google login)
                                          |- /admin        SPA + JSON API (Google login, session cookie)
                                          |- /health
                                          `- sync task --> Pluggy API (GET, POST /auth, POST /connect_token)
data/cashbook.duckdb (encrypted)   secrets/ (read-only mount)
```

## Storage and sync

- One DuckDB file, `data/cashbook.duckdb`, encrypted with DuckDB's native encryption. The key is `secrets/db.key`, generated by `cashbook-admin init`. The server refuses to start with a missing or wrong key.
- At startup the server runs migrations (copying the file to `cashbook.duckdb.bak-<version>` first), serves existing data and starts a background load. A full load runs daily at `REFRESH_AT` (timezone `TZ`); an hourly check calls `GET /items/{id}` and loads a connection when `lastUpdatedAt` advanced.
- Each connection merges in one transaction: rows Pluggy returned are upserted, rows inside the fetched date range that Pluggy no longer returns get `removed_at`, and older rows are left alone. That is how history outlives Pluggy's window. On error the transaction rolls back and the error is recorded on the connection.
- Disconnecting an alias deletes it and all its rows. There is no history carry-over between items.
- DuckDB runs with `memory_limit` 256 MB and `threads` 2; the container is limited to 512 MB.

## The SQL tool

`query_sql` accepts exactly one `SELECT` (or `WITH`) statement; the type comes from DuckDB's parser, not a regex. It runs on a separate reader connection opened after the encrypted file is attached and then locked with `enable_external_access=false` and `lock_configuration=true`: no files, network, extensions, `ATTACH`, `COPY`, `SET`, `PRAGMA`, `INSTALL`, `LOAD` or writes. Limits: 10 s timeout and 1,000 rows (with a `truncated` flag). Cells that contain an untrusted marker are listed in `suspicious_cells`.

## Untrusted text

Counterpart names, descriptions and payment messages are written by third parties. They are cleaned (the marker characters U+27E6 and U+27E7 are stripped), capped at 500 characters, and wrapped in `⟦untrusted:suspicious⟧ ... ⟦/untrusted⟧` when a heuristic flags them. Tool descriptions state that text columns are data, never instructions.

## Authentication

- The MCP connector uses Google OAuth through FastMCP. Only emails in `ALLOWED_EMAILS` are issued a token; redirect URIs are limited to `ALLOWED_REDIRECT_URIS` (the Claude callbacks by default).
- `/admin` uses a server-side Google OIDC login and a signed `HttpOnly`, `Secure`, `SameSite=Strict` cookie on `Path=/admin`. Mutating calls need `X-CSRF-Token` and a matching `Origin`; disconnecting needs recent re-authentication.
- Items added in `/admin` are validated server-side: `GET /items/{id}` must succeed with the server's API key, the connector must be MeuPluggy, and the item and alias must be unused.

## Read-only toward Pluggy

The Pluggy client makes GET requests plus `POST /auth` (API key) and `POST /connect_token` (the Connect widget). Nothing else is sent. `GET /v2/transactions` is used; the deprecated `GET /transactions` and `GET /identity` are never called.

## Threat model

Defended: unauthenticated access, prompt injection through transaction text, agent-written SQL, CSRF and replayed callbacks on `/admin`, foreign Pluggy items, theft of the disk or of a copy of the database file.

Not defended: a shell on the host. That attacker holds the Pluggy client secret and can read the current window live. Persistence adds two exposures: history older than Pluggy's window, and data that survives revoking the Pluggy credentials.
